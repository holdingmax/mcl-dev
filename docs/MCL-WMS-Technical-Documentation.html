1. Arquitectura General del Sistema

1.1 Patron Arquitectonico

MCL WMS es una Single Page Application (SPA) serverless construida sobre la plataforma Firebase de Google Cloud. No existen servidores propios ni infraestructura que gestionar: el frontend se sirve como archivos estaticos y toda la logica de backend se ejecuta en Cloud Functions bajo demanda.

1.3 Flujo de Informacion

  1. Usuario accede a https://wms-mcl.web.app via navegador
  2. Firebase Hosting sirve el bundle React (HTML/JS/CSS) desde CDN global
  3. React SPA se carga en el navegador y maneja toda la navegacion client-side
  4. Firebase Auth autentica al usuario (Google SSO o email/password)
  5. Firestore SDK (client-side) lee/escribe directamente a la base de datos
  6. Security Rules validan cada operacion segun rol y pertenencia del dato
  7. Cloud Functions ejecutan procesos automatizados (screening, alertas, limpieza)
  8. Cloud Storage almacena archivos binarios (PDFs, fotos, documentos)

2.4 Justificacion de Decisiones Tecnologicas

  • Firebase completo: Elimina la necesidad de mantener servidores, bases de datos o infraestructura. Escala automaticamente.
  • Firestore (NoSQL): Los datos logisticos son jerarquicos y variados. Un esquema flexible permite evolucionar sin migraciones.
  • Vite sobre Webpack: Build rapido (~3s vs ~30s), HMR instantaneo, code splitting nativo.
  • Tailwind CSS: Desarrollo UI rapido sin archivos CSS separados. Consistencia de diseno.
  • pdf-lib (client-side): Genera PDFs sin backend, reduce latencia y costos de Cloud Functions.
  • tesseract.js (client-side): OCR de etiquetas directamente en el navegador del operario de bodega.

3.3 Proceso de Deploy Actual

# 1. Build del frontend
npm run build          # Vite genera dist/

# 2. Deploy de hosting + reglas
firebase deploy --only hosting
firebase deploy --only firestore:rules
firebase deploy --only storage

# 3. Deploy de Cloud Functions
cd functions
firebase deploy --only functions

Configuracion de caching (firebase.json):

  • index.html: no-cache, no-store, must-revalidate (siempre fresco)
  • /assets/**: public, max-age=31536000, immutable (1 ano, versionados por hash)
  • SPA rewrite: todas las rutas redirigen a index.html

4.4 Buenas Practicas y Riesgos

Buenas practicas implementadas:
  • Secuencias atomicas (config/wr_sequence) con runTransaction() para evitar duplicados
  • client_ids como array para consultas array-contains en dispatches multi-cliente
  • Campos desnormalizados (client_name en bookings) para evitar JOINs costosos
  • Soft deletes en vendors (flag deleted en vez de borrar documentos)
Riesgos a mitigar:
  • Sin backups automaticos: Firestore no tiene backups programados por defecto
  • Desnormalizacion: Si cambia el nombre de un cliente, hay que actualizar todos los documentos relacionados
  • Limites Firestore: Max 1 escritura/doc/segundo. Batch max 500 docs
  • Consultas limitadas: Sin soporte nativo para OR, JOIN, ni full-text search

7c.4 Parseo de Emails — Patrones Regex

El agente parsea el body HTML de emails de Phantom K9. Soporta 3 patrones:

PatronFormatoEjemplo
Pattern 1AWB + ULD entre parentesis045-22209655 (84 PCS) ULD: PMC 45086QT
Pattern 2AWB + piezas en linea siguiente045-22209655\n84 PCS
Pattern 3aULD primero, coma, AWB piezas (sin parentesis)PAG72202R7 84, 045-22209655 84 PCS
Pattern 3bAWB primero, coma, ULD piezas045-22417080 1225, PAG62640R7 89 PCS

7c.5 Matching de AWBs

El agente busca el booking correspondiente en 3 pasos:

  1. Step 1 — awb_lines match: Busca el AWB en awb_lines[].awb_2nd_leg o awb_lines[].awb_number. Si encuentra, awb_line_index >= 0.
  2. Step 1b — Simple booking match: Busca en awb_2nd_leg o awb_1st_leg a nivel documento para bookings tipo simple. Si encuentra, awb_line_index = -2.
  3. Step 2 — MAWB match: Busca el AWB como mawb_number. Si encuentra, awb_line_index = -1.
  4. Step 3 — Fuzzy match: Busca sufijo numerico del AWB (ultimos 8 digitos) en cualquier campo.

7c.6 Deduplicacion ULD

Para evitar doble-conteo cuando el mismo ULD aparece en multiples emails:

  • El agente mantiene un set de processed_ulds por AWB
  • Si un ULD ya fue procesado para ese AWB, se ignora
  • El campo screening_events registra cada evento individual

7c.7 Retry de Eventos No Matcheados

Antes de procesar nuevos emails, el agente reintenta eventos con status unmatched o error. Esto permite que AWBs creados despues del email se asocien retroactivamente.

7d.6 Determinacion de Cargo Type

  • Si uld_type esta vacio o es "LOOSE" → LOOSE
  • Cualquier otro valor de uld_type → BUP

7d.7 Deteccion deliver_to

La funcion isDeliverToAirline() determina si la entrega es a una aerolinea o a una direccion fisica:

  • Sin deliver_to → asume aerolinea
  • Contiene patrones de direccion (numeros + AVE/STREET/etc.) → direccion
  • Contiene nombre de aerolinea conocida → aerolinea
  • Esto afecta si se genera ALL-IN o Handling Loose + Drop Off Loose

9. Riesgos Tecnicos y Recomendaciones

9.1 Puntos Fuertes del Sistema

FortalezaDetalle
Backups automaticos de FirestoreExport diario a las 5:00 AM UTC al bucket gs://wms-mcl-firestore-backups. Todas las colecciones, ~32 MB, ~3,000 docs. Verificar periodicamente que los exports se ejecuten.
Codigo versionado en GitHubRepositorio privado en github.com/MinCurllogistics/mcl-wms. Trazabilidad completa de cambios. Acceso para multiples desarrolladores.
Infraestructura serverlessFirebase Hosting + Cloud Functions. Escala automaticamente, sin servidores que mantener.
Screening automatizadoAgente que procesa emails K9 cada 5 minutos, con retry de eventos no matcheados y deduplicacion ULD.
Billing automaticoCargos generados al despachar vuelo, con recalculo, revision de facturas y soporte para cargos manuales.

9.4 Puntos Unicos de Falla (SPOF)

  1. Proyecto Firebase wms-mcl: Todo el sistema depende de este unico proyecto GCP.
  2. Cuenta Gmail de screening: Si se bloquea, el agente se detiene.
  3. Refresh token de Gmail: Si expira y no se renueva, screening y alertas fallan.
  4. Equipo de deploy: Codigo en GitHub pero deploy aun manual via CLI. Implementar CI/CD.
  5. Dominio MCL: Si el dominio expira, la autenticacion SSO falla.

9.5 Recomendaciones Prioritarias

ALTO — Implementar a corto plazo

1. CI/CD con GitHub Actions

  • Build automatico en cada push a main
  • Deploy automatico a Firebase Hosting
  • Deploy de Functions con aprobacion manual
  • Elimina dependencia de laptop personal

2. Entorno de staging

  • Crear segundo proyecto Firebase: wms-mcl-staging
  • Deploy automatico de branches a Preview Channels
  • Probar cambios antes de produccion

ALTO — Implementar en 30 dias

3. Tests automatizados

  • Unit tests para logica de billing (billing.ts, airBilling.ts)
  • Integration tests para Cloud Functions (screening parser)
  • E2E tests basicos para flujos criticos

5. Mover Anthropic API key a Secret Manager

  • Eliminar de config/anthropic_key en Firestore. Agregar como Firebase Secret.

6. Endurecer reglas de seguridad

  • delivery_tracking: Limitar updates a drivers con PIN valido
  • driver_queue: Rate limiting o validacion de datos minimos
  • vendors: Cambiar de read: if true a read: if isLoggedIn()

MEDIO — Implementar en 90 dias

7. Monitoreo y alertas

  • Alertas de Cloud Monitoring para errores en Functions
  • Alerta si processScreeningEmails falla 2+ veces consecutivas

8. Documentacion de API interna

  • Documentar formato esperado de emails de Phantom K9
  • Mantener types/index.ts como source of truth

9. Optimizacion de rendimiento

  • Paginacion en listas grandes
  • Lazy loading de fotos/PDFs
  • Cache con React Query o SWR

10. Control de versiones de reglas

  • Firestore y Storage rules se deben deployar via CI/CD. Nunca editar en consola.
